# 02 · 传输与协议

## 1. 通道优先级

| 优先级 | 通道 | 适用 | 失效条件 |
|---|---|---|---|
| ① | Wi-Fi + Bonjour 发现 | 同一路由器、未开客户端隔离 | 组播被拦 → 降级 ② |
| ② | Wi-Fi + 二维码直连 | 组播被拦但允许单播 | 客户端隔离拦单播 → 降级 ③ |
| ③ | BLE GATT | 任何网络环境 | 蓝牙关闭 / 距离过远 |

局域网直连场景需要 ① 和 ③；② 是网络受限时的中间档，成本低，建议一起做。

## 2. 发现

- 服务类型：`_voicerelay._tcp`
- 主机名：`voicerelay.local`（Bonjour 自动解析，二维码里同时给 IP 兜底）
- **端口固定 `8787`**：首版不做端口协商，Mac 端监听失败时直接在设置里换端口并重新生成二维码
- 实例名：`VoiceRelay-<设备简称>`（不暴露用户名）
- TXT 记录：

| Key | 含义 | 示例 |
|---|---|---|
| `v` | 协议版本 | `1` |
| `mid` | Mac 稳定标识（随机生成，非硬件 ID） | `a3f9…` |
| `port` | 监听端口（固定 8787） | `8787` |
| `name` | 展示名 | `Kevin 的 Mac` |

## 3. 二维码直连

二维码内容 = Base64URL(JSON)，字段全部可选，缺字段时回落到普通发现：

```json
{"v":1,"ip":"192.168.1.23","port":8787,"tok":"<一次性随机串>","exp":1732600000,"mid":"a3f9…"}
```

约束：

- `exp` 建议 120 秒；过期后二维码无效，但已建立的连接不受影响。
- `tok` 只用于首次握手，不写入日志。
- 二维码不包含 Mac 名称、用户名、蓝牙地址。

## 4. 帧格式（TCP 与 BLE 共用）

```
偏移  长度  字段
0     1     ver(4bit) | type(4bit)
1     1     flags(2bit) | seq(6bit)
2     2     len (uint16, 小端, 不含帧头)
4     len   payload
```

- `seq` 6 bit 循环，仅用于检测丢帧，不做重传。
- 控制帧 `len` 上限 4096；音频帧固定 40 ms 一包。
- BLE 传输时按 `MTU-3` 切片，接收端按 `seq` 重组；同一 `seq` 的分片不超过 32 个。

## 5. 消息类型

| type | 名称 | 方向 | payload |
|---|---|---|---|
| `0x1` | `HELLO` | 手机 → Mac | 协议版本、客户端类型、能力位 |
| `0x2` | `HELLO_ACK` | Mac → 手机 | Mac 名称、当前后端、权限状态位 |
| `0x3` | `AUTH` | 手机 → Mac | `HMAC(长期密钥, challenge)` |
| `0x4` | `AUTH_OK` | Mac → 手机 | 会话 ID |
| `0x5` | `STREAM_START` | 手机 → Mac | 采样率、通道数、编码格式 |
| `0x6` | `AUDIO` | 手机 → Mac | `seq(2) + timestamp(4) + opus 数据` |
| `0x7` | `STREAM_STOP` | 手机 → Mac | 总包数 |
| `0x8` | `RESULT` | Mac → 手机 | 最终文本、耗时、是否成功 |
| `0x9` | `LEVEL` | Mac → 手机 | 电平 0–100，50 ms 一次 |
| `0xA` | `CMD` | 手机 → Mac | 子类型 + 参数 |
| `0xB` | `CMD_ACK` | Mac → 手机 | 子类型 + 结果码 |
| `0xC` | `STATE` | Mac → 手机 | 前台 App、后端、权限摘要 |
| `0xD` | `ERROR` | 双向 | 错误码 + 人类可读信息 |
| `0xE` | `PING` / `PONG` | 双向 | 时间戳，10 s 一次 |

`CMD` 子类型：

| 值 | 动作 | 参数 |
|---|---|---|
| `0x01` | 切 App | bundleId（字符串） |
| `0x02` | 下一个输入框 | 无 |
| `0x03` | 上一个输入框 | 无 |
| `0x04` | 回车 | 无 |
| `0x05` | 退格 | 次数 |
| `0x06` | 切换后端 | `A` / `B` |
| `0x07` | 取消当前会话 | 无 |
| `0x08` | 复制最近一条文本 | 无 |
| `0x09` | 全选（⌘A） | 无 |
| `0x0A` | 撤销（⌘Z） | 无 |
| `0x0B` | 下一个 App（⌘Tab） | 无 |
| `0x0C` | 上一个 App（⌘⇧Tab） | 无 |
| `0x0D` | 当前 App 的下一个窗口（⌘`） | 无 |
| `0x0E` | 激活当前 App 的输入光标 | 无 |
| `0x0F` | Shift+Enter | 无 |

## 6. 握手与认证

首版不做证书体系，用"一次性码 + 长期密钥"：

1. 首次连接：Mac 界面显示 6 位确认码（或二维码直接携带 `tok`）。
2. 手机提交确认码，双方各自用 `HKDF(确认码, 随机数)` 派生出 32 字节长期密钥，存入 iOS Keychain / Android Keystore。
3. 之后每次连接：Mac 发 32 字节 `challenge`，手机回 `HMAC-SHA256(长期密钥, challenge)`。
4. 所有 `CMD` / `AUDIO` 帧带单调递增计数器（放在 `AUDIO` 的 timestamp 与 `CMD` 的 payload 首 4 字节），Mac 拒绝计数器回退的帧。
5. Mac 设置页提供"已配对设备"列表与"吊销"按钮。

蓝牙通道的安全等级不能只依赖 Just Works 配对，必须叠加上面第 3–4 步。

## 7. 背压规则（必须实现）

BLE 与 Wi-Fi 都会积压，不处理会把整条链路堵死（参考 SayAll 的 `watch-ble-audio-backlog` 问题）。

| 位置 | 规则 |
|---|---|
| 手机发送队列 | 上限 8 个 Opus 包（约 320 ms）；满了丢最旧，并在下一包标记 `gap` |
| Mac 接收缓冲 | 上限 2 秒音频；溢出时丢弃最旧，并回传 `ERROR(0x21)` |
| 音频优先级 | 按键帧插队，永远排在音频包之前发送 |
| 停止语义 | `STREAM_STOP` 必须等队列排空后再发，不能用 flush 代替 |

## 8. 错误码

| 码 | 含义 | 手机侧表现 |
|---|---|---|
| `0x10` | 认证失败 | 要求重新配对 |
| `0x11` | 协议版本不兼容 | 提示升级 Mac 端 |
| `0x20` | 识别引擎未就绪 | 禁用语音按钮 3 秒后重试 |
| `0x21` | 音频溢出 | 静默，仅日志 |
| `0x30` | 注入失败：无可用输入框 | 提示"当前没有可输入的位置" |
| `0x31` | 注入失败：Secure Input | 提示"密码框不支持语音输入" |
| `0x32` | 注入失败：目标 App 不支持 | 提供"复制文本"按钮 |
| `0x40` | 蓝牙不可用 | 提示打开蓝牙 |
| `0x50` | 后端不可用（虚拟声卡缺失） | 自动回落 A 后端并提示 |

## 9. 时序（正常一次输入）

```
手机                          Mac
 │── HELLO ──────────────────→│
 │←─ HELLO_ACK ───────────────│
 │── AUTH(HMAC) ─────────────→│
 │←─ AUTH_OK ─────────────────│
 │── STREAM_START ───────────→│
 │── AUDIO × N ──────────────→│  （Mac 边收边识别）
 │←─ LEVEL × M ───────────────│
 │── STREAM_STOP ────────────→│
 │                            │ 收尾识别 → 注入
 │←─ RESULT(text, ms) ────────│
```

超时约定：`STREAM_STOP` 后 5 秒没有 `RESULT`，手机显示"识别超时，可重试"。

后端 B 的 `RESULT` 使用 `ok=false`、`text=""`、`reason="ime_unconfirmed"`、`path="ime"`，表示音频已写入虚拟声卡，但无法确认输入法是否已经上屏；手机显示“已发送到输入法”，不显示“已上屏”。
