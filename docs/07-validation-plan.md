# 07 · 验证计划

> 目的：在写产品代码之前，用 5 个独立验证把"这个方案能不能成立"变成事实。
> 每个验证都必须有明确的**通过标准**和**终止条件**，不通过就改方案，不硬扛。

## 0. 排序原则

先验证"决定能不能做"的，再验证"决定好不好用"的。

```
S1 识别质量 ┐
            ├→ S3 注入 ┐
S2 公司网络 ┘           ├→ S4 BLE 兜底 → S5 虚拟声卡
                        ┘
```

S1 / S2 可以在一天内并行做完，它们决定项目是否继续。
S3 决定产品价值。S4 / S5 决定极端场景的可用性。

---

## S1 · sherpa-onnx 在本机跑通

| 项 | 内容 |
|---|---|
| 目标 | 确认 Intel + Ventura 上识别速度与中文质量可接受 |
| 依赖 | 官方 `sherpa-onnx-v2.0.3-osx-x64-static` 库、SenseVoice int8 模型 |
| 步骤 | ① 下载库与模型 ② 写一个最小命令行程序：读 WAV（16 kHz）→ 输出文本 ③ 跑 3 段真实录音：8 s 日常口语、15 s 中英混说、5 s 带数字金额 |
| 通过标准 | RTF < 0.5（8 s 音频推理 < 4 s，目标 < 2 s）；三段中文可读；数字/时间正确规范化 |
| 终止条件 | RTF > 1.2，或中文错误率明显高于手机自带输入法 → 改走云端 API 或改回虚拟声卡后端 |
| 产出 | `docs/` 里追加一节实测数据（RTF、内存、加载时间、三段结果对照） |
| 预估 | 0.5 天 |

**注意**：这一步不写 App 代码，只写一个临时命令行程序，验证完就丢。

---

## S2 · 公司网络连通性

| 项 | 内容 |
|---|---|
| 目标 | 确认在公司 Wi-Fi 下，哪条通道能用 |
| 步骤 | ① Mac 起一个最小 TCP 监听（可用 `nc -l`）② 手机用任意 TCP 工具连 `MacIP:端口` ③ 同时观察 Bonjour 能否发现 ④ 记录 macOS 防火墙弹窗行为 |
| 通过标准 | 至少一条可用：Bonjour 发现成功，或二维码直连（单播）成功 |
| 终止条件 | 单播也不通 → 公司场景只能靠 BLE，需要把 BLE 从"兜底"提到"并列主通道" |
| 产出 | 一张表：公司 Wi-Fi 下 Bonjour / 单播 / BLE 三项的结果 |
| 预估 | 0.5 天 |

**要记录的环境信息**：SSID 类型（企业/访客）、是否 802.1X、是否有零信任客户端、Mac 是否 MDM 管理（对应 Q-01）。

## S3 · 文本注入矩阵

| 项 | 内容 |
|---|---|
| 目标 | 确认三级注入在常用 App 上的实际成功率 |
| 步骤 | 写一个临时工具，对以下 App 逐一测试三种注入路径：备忘录、Chrome（网页输入框）、VSCode、飞书、微信、Xcode |
| 测试文本 | 短句 8 字、长句 40 字、中英混排、带数字与标点 |
| 通过标准 | 每个 App 至少有一条路径成功；Chrome/VSCode/飞书/微信四个必须覆盖 |
| 终止条件 | 飞书或微信只有粘贴能过，且粘贴恢复剪贴板不稳定 → 默认后端要考虑改回虚拟声卡 |
| 产出 | 6 × 3 的成功矩阵 + 每种失败的具体表现 |
| 预估 | 0.5 天 |

---

## S4 · BLE 音频兜底

| 项 | 内容 |
|---|---|
| 目标 | 确认 BLE 能稳定传 10 分钟语音，不积压、不堵死 |
| 步骤 | Mac 用 `CBPeripheralManager` 广播 + notify；手机（先用 Mac 上的模拟客户端）每 40 ms 发一包 80 字节 |
| 通过标准 | 连续 10 分钟无积压；末端延迟 < 300 ms；主动丢帧后能自动恢复 |
| 终止条件 | 稳定吞吐 < 20 kbps，或延迟抖动 > 500 ms → BLE 只传按键，不传音频 |
| 产出 | 吞吐、延迟分布、丢帧率 |
| 预估 | 1 天 |

**必须先实现背压**（发送队列上限 8 包、丢最旧），否则测出来的数据没意义。

---

## S5 · 虚拟声卡与输入法

| 项 | 内容 |
|---|---|
| 目标 | 确认 B 后端在你实际使用的输入法上可用 |
| 步骤 | ① 装原版 BlackHole 2ch ② 在豆包 / 微信输入法设置里看能否选到该设备 ③ 用 QuickTime 录音确认有电平 |
| 通过标准 | 输入法能看到设备并正常收音 |
| 终止条件 | 输入法不显示该设备 → 需要按 SayAll 的做法改造（伪装 USB transport），成本 +2 天；或放弃 B 后端 |
| 产出 | 结论 + 输入法版本号 |
| 预估 | 0.5 天 |

---

## 总时间与决策点

| 阶段 | 累计 | 决策 |
|---|---|---|
| S1 + S2 | 1 天 | 项目是否继续、公司场景走哪条通道 |
| S3 | 1.5 天 | 默认后端是 A 还是 B |
| S4 + S5 | 3 天 | BLE 是否传音频、B 后端是否保留 |

全部通过后，才开始建工程（Flutter + Xcode）。

## 明确不在验证范围内

- UI 还原度（原型阶段不做）
- 多设备、账号、同步
- 云端识别
- 安装包与签名流程见 [`RELEASING.md`](RELEASING.md)
