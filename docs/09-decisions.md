# 09 · 决策记录

> 格式：背景 → 决策 → 后果。编号固定，后续变更用 D-xx 追加，不覆盖旧条目。

---

## D-01 · 手机端用 Flutter

**背景**：需要同时支持 iOS 15+ 与 Android（无 GMS），但手机端只有三个界面。

**决策**：Flutter 做 UI 与状态机；BLE、录音、后台保活写成平台通道（Swift / Kotlin），不用现成插件兜底。

**后果**：一套 UI；但 BLE 与音频的边界情况需要自己写两遍原生代码。若插件出问题，排查成本高于原生。

---

## D-02 · 识别放在 Mac，用 sherpa-onnx

**背景**：Android 无 GMS，系统语音识别不可用；Mac 是 Intel，跑 Whisper 中文太慢。

**决策**：默认后端为 Mac 本地 sherpa-onnx（SenseVoice int8 整段识别），手机只负责采集与传输。

**后果**：手机端极薄，不受厂商语音服务差异影响；代价是音频必须实时传到 Mac，网络成为硬依赖（由 BLE 兜底补上）。

---

## D-03 · 保留虚拟声卡作为第二后端

**背景**：第三方输入法（豆包 / 微信）的识别质量高于本地小模型。

**决策**：保留"写虚拟声卡 + 注入输入法语音键"这条路径，作为可切换后端 B；默认仍是 A。

**后果**：多一套权限（输入监控）与一份安装包（pkg）。两条路径必须互斥，切换要重启会话。

---

## D-04 · Wi-Fi 为主，BLE 兜底

**背景**：公司 Wi-Fi 大概率客户端隔离；BLE 带宽只够 20–30 kbps。

**决策**：Wi-Fi（Bonjour + 二维码直连）承载音频；BLE 作为网络不可用时的备用通道，只传音频与按键。

**后果**：需要维护两套传输实现；BLE 必须实现背压，否则会堵死链路。

---

## D-05 · 不做自建输入法

**背景**：早期方案考虑用 `IMKInputController` 把文字直接插进输入框。

**决策**：放弃。既然自己做了识别，就不需要输入法容器；输入法路径只通过虚拟声卡复用现成的第三方输入法。

**后果**：省掉输入法 bundle 的签名、加载、进程生命周期管理；代价是失去"输入法级"的绝对兼容性，改用 AX / 粘贴注入。

---

## D-06 · 完全自用，不考虑分发

> **已被 D-13 取代（2026-11-27）**：项目转为 MIT 开源，并通过 GitHub Releases 分发 DMG / APK。以下内容保留作历史记录。

**背景**：单人使用，单一 Mac。

**决策**：不做公证、不上架、不做多设备、不做账号、不做自动更新。iOS 直装真机，Android 直接装 APK。

**后果**：可接受"未签名警告"和"手动授权"；也意味着不能依赖任何需要审核的能力。

---

## D-07 · 传输用自定义二进制帧，不用 JSON

**背景**：BLE 上 JSON 开销大，音频包 40 ms 一个。

**决策**：固定帧头 `ver/type/seq/len`，控制帧 payload 用紧凑 JSON（低频），音频帧纯二进制。

**后果**：需要自己写编解码两端一致性测试；换来带宽与解析确定性。

---

## D-08 · 认证用应用层 HMAC，不依赖蓝牙配对

**背景**：macOS 作为 BLE 外设时系统级绑定支持弱。

**决策**：首次确认码派生长期密钥，之后每条指令带计数器 + HMAC，Mac 拒绝重放。

**后果**：多一层实现，但把"远程键盘"的风险降到可接受。

---

## D-09 · 注入顺序固定为 AX → Unicode → 粘贴

**背景**：没有任何一种注入方式能覆盖全部 App。

**决策**：固定降级顺序，不允许跳级；长文本（> 12 字）直接走粘贴。

**后果**：需要为每个 App 维护一条"实测记录"，S3 产出这张表。

---

## D-10 · V1 用整段识别，不上流式

**背景**：按住说话的交互本身就是"松手出字"。

**决策**：V1 用 SenseVoice 整段识别，省掉标点模型与流式状态机。

**后果**：无实时预览；如果实测端到端超过 1 秒，再切流式 zipformer + 标点模型（V2 预留）。

---

## D-11 · 端口固定 8787，主机名 voicerelay.local

**背景**：原型里 Mac 设置页显示只读端口 `8787`，向导页显示 `voicerelay.local:8787`。

**决策**：自用不做端口协商，固定监听 8787；Bonjour 主机名固定 `voicerelay.local`，二维码里同时给 IP 兜底。

**后果**：端口被占用时需要手动改端口并重新生成二维码；换来手机端零配置。

**备注**：原型提供视觉与交互参考；文案与技术口径冲突时以文档为准，见 D-12。

---

## D-12 · 文档是工程准绳，原型是视觉参考

**背景**：原型交付后发现 4 处与既定决策冲突（模型名、手机侧识别文案、权限重启提示、状态条数量）。

**决策**：`docs/03`、`docs/04` 描述**要实现的界面**，为工程唯一依据；原型用于评审视觉与交互。冲突时改原型，不改文档。

**后果**：需要维护一份修正记录（`README.md` 第四节）；本次 5 处已于 2026-11-26 全部改完，当前原型与文档一致。

---

## D-13 · 转为开源项目（MIT）

**背景**：v1.0.0 已能完成"按住说话 → 文字上屏"的完整链路，需要让其他人能安装、复现、验证硬件并一起维护。

**决策**：代码以 **MIT** 开源；安装包通过 GitHub Releases 分发（`VoiceRelay-*.dmg` + `VoiceRelay-*.apk`）；**不打包模型权重**，App 首次运行从 sherpa-onnx 官方 Release 下载；接受"未公证"的首次打开提示；APK 暂用 debug 签名侧载。

**后果**：D-06 作废。需要长期维护安装说明（`docs/INSTALL.md`）、贡献指南、第三方许可证（`THIRD_PARTY_NOTICES.md`）和发布流程（`docs/RELEASING.md`）；协议与 UI 变更要考虑向后兼容；正式签名/公证/上架需要维护者自备证书与账号。

---

## 已推翻的决策

| 曾经的想法 | 为什么放弃 |
|---|---|
| 自建 IMKInputController 输入法 | 识别自己做之后完全多余，见 D-05 |
| 手机端做 ASR | 无 GMS 的 Android 不可用，见 D-02 |
| 用 CGEvent 逐字打长中文 | 走输入法管道会丢字，见 D-09 |
| 用 Cmd+Tab 模拟切 App | 顺序不可控，改用 `NSRunningApplication.activate` |
| 纯 BLE 传音频 | 带宽与稳定性不足，降级为兜底，见 D-04 |
